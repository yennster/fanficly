# AGENTS.md — working in Fanficly for Windows

Architecture, workflow and regression rules for agents working on the Windows app in `windows/`. Claude Code loads this file through `windows/CLAUDE.md` when you work in this folder; the repository-wide rules and the Apple app's guide are in the root [`AGENTS.md`](../AGENTS.md). Read "What this is" and "Start here" first, then the section for the part you're changing. Keep this file current when behaviour or ownership changes, and check details against the source rather than trusting older notes.
Picking up roadmap work? Go straight to [Autonomous roadmap work](#autonomous-roadmap-work).

## What this is

A native Windows app (WinUI 3 on the Windows App SDK, C# on .NET 10, Native AOT in Release, MSIX for the Microsoft Store, x64 and ARM64, Windows 10 2004 / build 19041 and later) that reads AO3 fanfiction. It is a port of the SwiftUI app on `main`. There is no AO3 JSON API, so the app scrapes AO3's HTML with AngleSharp, through one `HttpClient` with a custom `User-Agent` and a 1 request/second throttle. Everything runs on the PC: no servers, no analytics.

Both apps live on `main`: the Apple app in `apple/` (`apple/Fanficly/`, `apple/FanficlyTests/`, …) and this one in `windows/`. The Swift sources are the reference implementation. Most C# types name their Swift counterpart in a doc comment ("SwiftData's `@Query`", "the Mac's swipe action"); when behaviour is unclear, the Swift code is the specification. The Apple app's own guide is [`apple/AGENTS.md`](../apple/AGENTS.md).

## Start here

- **Build truth:** `windows/Fanficly.Windows.slnx`, `windows/Directory.Build.props`, `windows/Directory.Packages.props` (central package versions) and `windows/global.json` (SDK 10.0.100, `rollForward: latestFeature`). There is no XAML markup and no generated project to regenerate: adding a `.cs` file under a project folder is enough.
- **Product rules:** reading, search, Browse, Popular and local follows need no account. AO3 bookmarks, subscriptions, posting comments and leaving kudos need login. Follow is not subscribe; saved chapter text is not an EPUB download. Never guess tags from keywords.
- **Data safety:** keep offline chapter text, timestamped progress, subscription notification baselines and forward-only backup merges intact. The library is a local SQLite file, not a cloud database; sync is an opt-in file in a folder the user picks.
- **Network and privacy:** every AO3 request goes through `IAO3Client` and its throttle. No telemetry, no backend. Never log passwords, cookies or keys (`AppHost.Log` writes a local file).
- **Validation:** `dotnet test` on the Core tests runs anywhere. The app compiles on Linux and macOS, but running it and the UI tests needs Windows (or CI). See [Tests](#tests) and [Which machine you're on](#which-machine-youre-on).
- **Related docs** (all in `windows/`): `README.md` (features and setup), `CONTRIBUTING.md`, `ACCESSIBILITY.md`, `PRIVACY.md` (linked from the Store listing, so keep it accurate), `MICROSOFT_STORE.md` (packaging, listing, release tags), `ROADMAP.md`; plus `.github/workflows/windows-ci.yml` and `windows-store.yml`.

## Architecture

Two projects carry the app:

- **`Fanficly.Core`** (`net10.0`, no Windows APIs): the AO3 client and parsers, search syntax, the SQLite library, sync merging, stats, subscriptions polling, deep links, widget data, and the reader's pure layout logic. All of it lives in the single namespace `Fanficly.Core`. Its tests run on any OS.
- **`Fanficly.App`** (`net10.0-windows10.0.26100.0`): the WinUI shell, screens, and Windows integrations (toasts, widgets, background task, jump list, gamepad, DPAPI cookie vault, Store review).

```text
Program.Main (STA; COM-server modes; single-instance redirect)
  └─ App.OnLaunched → AppHost.Initialize (services) → MainWindow
       ├─ NavigationView sidebar → Tabs.Root(item) → Screen
       │    └─ Navigator stack: Push / ReplacePath / GoBack
       │         └─ Routes.* factories (work page, author, comments, login, …)
       ├─ IAO3Client → AO3Client → Throttle → HTTP → pure parsers → records
       ├─ LibraryStore (SQLite) → WorkPersistence / ReadingProgressStore / stats
       └─ LibrarySyncManager → library_backup.json in the sync folder
Widgets COM server / background task (separate processes) → same Core stores
```

**The UI is code-only WinUI.** Screens build ordinary WinUI controls in C# with the helpers in `UI/Kit.cs`; there is no XAML markup, no `x:Bind`, no data templates in markup. `App` implements `IXamlMetadataProvider` (forwarding to `XamlControlsXamlMetaDataProvider`) and `Main` lives in `Program.cs` (`DISABLE_XAML_GENERATED_MAIN`). That's why the app compiles and type-checks on any OS.

**`Screen`, `Navigator`, `MainWindow` (in `Shell/`).**
- `Screen` is the base class for every page: `Title`/`Subtitle`, `ShowsHeader`, `PrefersFullWindow`, a lazily built `View` (override `Build()`), `PrimaryCommands`/`SecondaryCommands` for the header's command bar (call `InvalidateChrome()` when they change), `OnAppearing`/`OnDisappearing`/`OnRemoved`, `HandleKey(VirtualKey, modifiers)` and `HandleBack()`.
- `Navigator` is one tab's stack: `SetRoot`, `Push`, `ReplacePath` (replace everything above the root), `GoBack` (asks the top screen's `HandleBack` first), `Remove`, `PopToRoot`, `Depth`, `CanGoBack`, and a `Changed` event.
- `MainWindow` owns the `TitleBar`, the `NavigationView` sidebar (Settings in its footer), the header (title, subtitle, command bar), the message area for InfoBars (`ShowMessage`, which also announces to Narrator), zoom, full screen and window placement. `MainWindow.Current` is the one window. Clicking the selected tab again pops it to its root.

**`Tabs` and `Routes` are registries filled from `[ModuleInitializer]`s.** Each feature folder registers itself, so the shell never references feature screens directly:
- `Views/Tabs.cs`: `Tabs.Register(SidebarItem, Func<Screen>)` and `Tabs.Root(item)` (a `PlaceholderScreen` saying "Coming soon." when nothing registered).
- `Views/Routes.cs`: factories `WorkDetail`, `SavedWork`, `Resume`, `AuthorWorks`, `FilteredWorks`, `Comments`, `Bookmark`, `Login`; actions `Import` and `LibraryFolder`; the `SearchRequested` event. Call the helpers (`Routes.OpenWork`, `OpenSavedWork`, `OpenAuthor`, `OpenFilteredWorks`, `OpenComments`, `OpenBookmark`, `OpenLogin`, `RequestSearch`); a missing factory pushes a placeholder rather than crashing.
- Registrations today: `BrowseRegistration` (Browse, Popular, `FilteredWorks`), `SearchModule` (Search), `LibraryModule` (Library, Stats, `LibraryFolder`), `HistoryRegistration` (Recently Viewed), `AuthorsModule` (Authors, `AuthorWorks`, and the notification-permission prompt), `AccountModule` (Subscriptions, Bookmarks, `Login`, `Comments`, `Bookmark`), `SettingsModule` (Settings), `ImportOverlay` (`Import`), `ReaderModule` (`WorkDetail`, `SavedWork`, `Resume`; see [the reader](#the-reader-listen-export-and-reading-position)).

**Module initializers must not create XAML objects.** They run when the assembly loads, before `Application.Start` brings the XAML runtime up, and creating a `FontFamily`, brush, style or any `DependencyObject` there crashes the app at launch. Registering factories (lambdas) is fine. `Symbols.Font` is lazy for exactly this reason (`SettingsModule` calls `Symbols.Add` from its initializer), and `SearchModule.EnsureSymbols()` adds its icons from the UI thread when the screen is first built. Keep static field initializers of anything a module initializer touches free of XAML objects too.

**Launch, in order (`App.OnLaunched`):** add `XamlControlsResources`, `Theme.InstallAccent`, `AppHost.Initialize()` (services, below), create `MainWindow` with `RootFactory = Tabs.Root`, `AppHost.OnWindowCreated`, `AppearanceSettings.Apply()`, `RestoreBanner.Attach`, `Window.Start(AppHost.InitialTab)` (else the saved `app.selectedTabRaw`, else Search), `Activate()`, the 17+ age gate (`ContentSafetyViews.EnsureAgeGateAsync`), then `AppHost.HandleActivation(..., isLaunch: true)`. Unhandled exceptions are logged and marked handled.

**Services (`Services/AppServices.cs`, `AppHost.InitializeServices`).** `AppHost.Client`, `AppHost.Library`, `AppHost.Auth` and `AppHost.Sync` are the process-wide services.
- Normal run: `AO3Client`, `LibraryStore.Open(AppPaths.Database)` (a damaged file, SQLite's CORRUPT or NOTADB, is moved aside as `library.sqlite.damaged-<timestamp>` and a fresh one opened; any other failure, such as a lock, retries twice a second apart and then runs on an in-memory library with sync off and an error banner, never setting the file aside), `ProtectedCookieVault` as `CredentialStore.Shared`, the shared widget store as `AppGroupStore.Shared`, and `LibrarySyncManager` on the folder in `settings.syncFolder`. It then installs the cloud-sync observers (`WidgetProgressStore`, `ReaderProfileSyncStore`, `StreakStore`), registers toast notifications, starts `InAppPolling` and registers the background task.
- `InstallLibraryHooks` wires Core's `LibraryHooks` (streak on a read, last-read widget plus jump list on progress, widget data refresh) and queues a backup on every `LibraryStore.Changed`.
- `RunLaunchTasksAsync` restores from the sync folder when sync is on and the backup changed since this PC last applied or wrote it, proposes EPUB re-downloads, runs `ReadingStatsBackfill`, and refreshes widget data.
- On close: save the library, back up if sync is on, flush the synced settings and the widget store.

**Concurrency.** `IAO3Client` methods are async and thread-safe; `Throttle` serializes them. `LibraryStore` takes one lock per call so the UI and the poller can share it, but records aren't locked: mutate a given record from one thread at a time. `LibraryStore.Changed` is raised on the saving thread; screens subscribe through `LibraryChanges` (in `Views/Browse/`), which marshals to the UI thread and coalesces bursts. Never touch XAML objects off the UI thread; hop with `DispatcherQueue.TryEnqueue`. Keep cancellation tokens flowing, and never retry a POST.

## Storage map

| Data | Where | Notes |
| --- | --- | --- |
| Library records | `LibraryStore` over `library.sqlite` (`AppPaths.Database`) | Identity map loaded at open (chapter bodies lazily). Mutate, `Insert`/`Delete`, then `Save` (one transaction, diffed against what was last written), which raises `Changed` with `LibraryEntityKinds`. |
| Settings (the `@AppStorage` stand-in) | `KeyValueStores.Default` = `JsonFileKeyValueStore(AppPaths.Settings)` (`settings.json`, flushed after 300 ms) | Reader typography keys are per device: always `ReaderProfile.DeviceKey(...)` (suffix `.windows` here). |
| Synced settings (the iCloud key-value stand-in) | `KeyValueStores.Synced` = `SyncFolderKeyValueStore` (`Shared/synced.json`, copied to `<sync folder>/fanficly-settings-sync.json`) | Push debounced 1 s, pull 500 ms after the file changes; last writer wins per key. Carries reader profiles, last-read progress and the streak. Only reaches the folder while sync is on, unlike iOS where key-value sync is always on. |
| Widget data (the app-group stand-in) | `AppGroupStore.Shared` = `Shared/group.json` (`WidgetStorage.SharedStorePath`) | Read by the widgets COM server, which re-reads from disk before every update. |
| AO3 login | `ProtectedCookieVault`: `Credentials/ao3_username.bin` and `ao3_cookies.bin`, DPAPI-encrypted for the current Windows user | Passwords are never stored. |
| EPUB files | `AppPaths.Downloads\<id>.epub` | `AO3Client.DownloadEpubAsync` writes into the folder the client is built with (`AppPaths.Downloads`, in `AppServices` and the background task); `WorkPersistence.EpubPath` looks in `WorkPersistence.LibraryFolder`, set to the same folder at launch, for the Downloaded state. Keep the two in step. |
| Exports | `%TEMP%\Fanficly\Exports` (`AO3Client.ExportsDirectory`) | Temporary files for the share sheet and "Save a copy as". Not the library. |
| Log | `Logs/fanficly.log` (`AppHost.Log`), deleted and restarted past 512 KB; Debug output only in demo mode | Never sent anywhere. Never log secrets. |
| Library backup | `<sync folder>/library_backup.json` (`LibrarySyncManager`) | Same JSON format as the Swift backup, so a Mac and a PC can share one iCloud Drive folder. |

`AppPaths.LocalData` is the package's `ApplicationData.Current.LocalFolder` when installed from MSIX, else `%LOCALAPPDATA%\Fanficly`. `AppPaths.IsPackaged` says which.

Mutations go through `WorkPersistence` (Upsert, UpsertMetadata, ToggleFollow, Unfollow, ToggleStar, TogglePin, DeleteWork, folder operations, RecordView, ToggleFollowAuthor), which saves and calls `LibrarySyncManager.QueueBackupShared`. `QueueBackup` refreshes widget data even with sync off, then debounces the backup by 2 s. Reading-position and reading-time saves (`ReadingProgressStore.Save`, `ReadingStatsStore.Record`) save inside `LibrarySyncManager.ReadingActivity()`, so the `Changed` hook queues the slow backup instead (`ActivityBackupDebounce`, 5 minutes, not pushed back by more reading, brought forward by any other change; closing the app backs up anyway), rather than rewriting the whole library every 1.5 s while reading (#137). A raw `store.Save()` does neither. `TrySave` logs a failure and raises `LibraryHooks.SaveFailed`, which shows "Couldn't save your library" (at most once a minute); the change stays pending and every later save retries it. New rows move past the table's highest id at save time, so rows another process wrote (the background task, a second copy of the app) can't make every save fail on a duplicate id. `UpsertMetadata` keeps chapter bodies; `Upsert(payload)` replaces them. Chapter indices are one-based and paragraph indices zero-based; keep them aligned across parsing, rendering, speech, pagination, saved anchors and resume URLs.

## Build & run

All commands run from `windows/`. You need the .NET 10 SDK.

```bash
dotnet test tests/Fanficly.Core.Tests            # unit tests (any OS)
dotnet build src/Fanficly.App -p:Platform=x64    # compile the app (any OS; ARM64 too)
dotnet build tests/Fanficly.UITests              # compile the UI tests (any OS)
```

Off Windows, `EnableWindowsTargeting` lets the Windows projects compile and the csproj turns off MakePri and MSIX tooling, so a Linux build proves the code compiles but produces nothing runnable.

Run on Windows (unpackaged, self-contained):

```powershell
dotnet build src/Fanficly.App -c Debug -p:Platform=x64 -p:WindowsPackageType=None `
  -p:WindowsAppSDKSelfContained=true -p:RuntimeIdentifier=win-x64 -o ../artifacts/app-x64
../artifacts/app-x64/Fanficly.exe -demoMode
```

Launch arguments: `-demoMode` (offline `DemoAO3Client`, in-memory library and settings, demo login `demo_reader`, no toasts or review prompts, no age gate), `-set key=value` (demo mode only, repeatable: presets a setting in the in-memory store, e.g. `-set reader.mode.windows=pageByPage`), `-demoLongChapters` (long demo chapters for page layout), `-tab <raw>` (`search`, `browse`, `popular`, `library`, `recentlyViewed`, `authors`, `bookmarks`, `markedForLater`, `ao3History`, `subscriptions`, `stats`, `settings`), `-iconGallery` (pushes `IconGalleryScreen`, every icon the app uses, so a glyph missing from the installed font shows as an empty box). A `fanficly:` or AO3 `https:` link among the arguments is opened too; the reader layout tests pass `fanficly://resume/90001`. `-RegisterProcessAsComServer` and `-BackgroundTask` are for Windows to start the widget and background-task servers; don't pass them by hand.

Unpackaged runs have no package identity, so the Widgets board, the background task, the share target, the `fanficly://` protocol and the Store rating dialog don't work there; in-app polling, toasts and the jump list are attempted but may not show. Deploy the packaged app from Visual Studio (WinUI application development workload) to test those. The Store bundle (Release, Native AOT, x64 + ARM64) is built with MSBuild as in `windows-ci.yml`'s `package` job and in `README.md`; releasing is in `MICROSOFT_STORE.md`.

## Tests

**Core tests** (`tests/Fanficly.Core.Tests`, xUnit, 643 cases in 43 files, all fixture-based, no network). They pass on Linux, macOS and Windows.
- **Parsers:** `SearchResultsParserTests` (incl. the bookmarks page), `WorkPageParserTests` (incl. login, comments and bookmark-form parsing), `KudosParserTests` and `KudosGiverTests` (in `KudosTests.cs`), `SubscriptionsParserTests` (fails closed), `MediaCategoryParserTests`, `WorkMetadataParserTests`, `HtmlDomTests`.
- **Networking:** `AO3ClientTests` (through a fake `HttpMessageHandler`: retries, cookies, redirects, timeouts, form posts), `AO3EndpointsTests`, `ThrottleTests` (spacing, and concurrent waiters serialized), `DemoAO3ClientTests`.
- **Search:** `SearchSyntaxTests`, `SearchSuggestionsTests`, `AO3SearchFiltersTests`, `TagResolverTests` (with `StubAO3Client`), `FandomCatalogTests`, `BrowseModelsTests`, `PopularStoreTests`.
- **Library and sync:** `LibraryStoreTests` (identity map, save diffing, migrations, relationships), `PersistenceTests`, `LibraryBackupJsonTests` (the Swift backup format), `SyncFolderSuggestionsTests`, `LibrarySortTests`, `ReadingStatsRecordTests`, `ReadingSpeedTests`, `StreakStoreTests`, `CrossAreaTests`.
- **Reader logic:** `HTMLToAttributedTests`, `ChapterTrackingTests`, `ReaderMetricsTests` (spread rule, page-area tracking, and `ReaderPaginator` across a device matrix with `FakeTextMeasurer`), `ReaderProfileTests` (merge, tombstones, per-device keys).
- **Routing and widgets:** `DeepLinkTests`, `NotificationRouteTests`, `ResumeProgressPolicyTests`, `WidgetDataStoreTests`, `WidgetProgressStoreTests`.

Tests that touch the static stores (`KeyValueStores`, `AppGroupStore`, …) join `[Collection(GlobalStoreCollection.Name)]` so they don't run in parallel. Core's internals are visible to the test project, so make a helper `internal` (not `public`) when it needs direct testing.

**UI tests** (`tests/Fanficly.UITests`, FlaUI over UI Automation, Windows only). `AppSession` launches `FANFICLY_EXE` (default `windows/artifacts/app-x64/Fanficly.exe`) with `-demoMode` at a form factor (Desktop 1600×1000, Tablet 834×1112, Compact 420×880, and for Store art Store 1200×750 at `-captureScale 2.4` and StoreTablet 834×1112 at `-captureScale 2`) and finds elements by automation id.
- `SmokeTests`: launch, every tab from its Ctrl shortcut (laptop and compact), the tabs without one (Marked for Later, AO3 History) from the sidebar and `-tab`, sidebar selection, `-tab`, back, zoom and F11, a second launch handed to the running window, a `fanficly://search` link, and Settings → About reading its text from the resource table. `SmokeTests.Accessibility.cs` (same partial class, so CI's `SmokeTests` filter runs it) checks the Narrator names of the icon-only buttons on Library, Stats, Subscriptions and Settings → Theme & typography by automation id.

## Conventions

- **`IAO3Client` is the only seam to the network.** Screens use `AppHost.Client`; nothing else creates an `HttpClient`. Implementations: `AO3Client` (live), `DemoAO3Client` (demo mode), `MockAO3Client`; tests also use `StubAO3Client` and `PollerFakeClient`. A new interface method needs all of them.
- **Throttle.** Every request waits on the client's `Throttle`. Never bypass it, never parallelize scrapes.
- **Parsers are pure.** They take an HTML string and return records. Use `HtmlDom` helpers, which reproduce the SwiftSoup calls the Swift parsers make. AngleSharp follows CSS strictly: attribute values in selectors must be quoted (`a[href^='/tags/']`), unlike jsoup.
- **Native AOT.** Release builds are trimmed and compiled ahead of time (`PublishAot`, `IsAotCompatible` on both projects, the CsWinRT AOT optimizer). So: no `System.Text.Json` serializer or reflection-based binding (JSON is hand-written with `Utf8JsonWriter`/`JsonDocument`, see `LibraryJson`, `LibraryBackupJson`, `WidgetJson`); no runtime code generation, `dynamic` or `Activator` on unknown types; WinRT types you implement are `partial` classes so CsWinRT can generate their vtables (see the widget provider and class factories); lists hand ItemsRepeater boxed indices (`VirtualList<T>`) rather than arbitrary C# objects. Treat any new trim or AOT warning as an error and fix it. The Debug build is JIT, so AOT problems show up only in the Release `package` job.
- **Settings go through `KeyValueStores.Default`** (or `.Synced` for the few synced channels), not custom files. Reader typography keys always go through `ReaderProfile.DeviceKey(...)`.
- **Dependencies.** Only AngleSharp and Microsoft.Data.Sqlite at runtime (plus the Windows App SDK). Versions live in `Directory.Packages.props`. Don't add analytics, crash reporters or any SDK with a network side channel.
- **Never show a dialog from menu content.** A `MenuFlyout` item's handler defers through the dispatcher (`AfterMenu` in `LibraryActions`, `Later` in `SearchScreen`/`StatsScreen`) so the flyout has closed before a `ContentDialog` opens. Open dialogs only through `Dialogs` (`AlertAsync`, `ConfirmAsync`, `PromptAsync`, `SheetAsync`, `ShowAsync`): WinUI allows one `ContentDialog` per window at a time, and `Dialogs` queues them.
- **UI helpers.** Build screens with `UI.UI.*` (`VStack`, `HStack`, `Grid`, `Text`, `Secondary`, `Caption`, `SectionHeader`, `Icon`, `Button`, `IconButton`, `ToolbarButton`, `Card`, `Chip`, `EmptyState`, `Loading`, `Scroll`, `Section`, `SettingsRow`, `NavRow`, `Toggle`, `MenuItem`, `CheckItem`, `Menu`, `Flow`, `Banner`, …) and the `ElementExtensions` (`A11y`, `A11yHeading`, `A11yHidden`, `Tip`, `Shortcut`, `OnTapped`, `Margin`, …). Settings pages use `SettingsKit`; `UI.SettingsRow` moves a wide control under its label below 440 px, like Windows Settings' cards. Where the Mac uses a segmented `Picker`, use `Segmented` (it drops its icons below 130 px a segment so the titles fit). Chips, tokens and tags have 4 px corners (Windows' token style), not the Mac's capsules. Icons are named by their SF Symbol name and mapped in `Symbols` (`Symbols.Add` for new ones). Pick glyphs Segoe Fluent Icons actually has: the icon gallery test fails on any it can't draw. For an icon it lacks on some PCs (the bookmark ribbon, a filled bell), add path markup to `Symbols.Drawn` (a 16-unit grid, 1-unit stroke, nonzero fill) and create icons with `Symbols.Icon`/`UI.Icon`, never `new FontIcon { Glyph = … }`, so the drawn ones work everywhere.
- **User-facing text comes from `Strings.Get("Screen_Thing")`** (`Services/Strings.cs`, RM-109), backed by `Strings/en-US/Resources.resw`: the Windows half of the Apple app's String Catalog. English only for now. Moved so far: Settings → About; the rest is RM-117, one screen per PR. Keys use `_`, never `.` (MRT reads a dot as a XAML property path). AO3 data (tag, category and fandom names, titles) stays verbatim and never goes in the table. The SDK picks up every `*.resw` as a `PRIResource`, so the csproj needs nothing; MakePri builds the table into `resources.pri` only on Windows, so with a missing or stale `resources.pri` `Strings.Get` returns the key itself. `ResourceStringsTests` (Core, any OS) checks every key in the code has an entry and every entry is used; `SmokeTests.AboutReadsItsStringsFromTheResourceTable` checks the lookup in the built app.
- **Colours come from `Theme`.** Brushes are swapped in place when the theme changes, and in high contrast they become the system colours. Don't hard-code colours in a screen.
- **Automation ids** are lowercase, dotted `<area>.<thing>`: `sidebar.<raw>`, `header.title`, `header.commands`, `search.box`, `library.search`, `library.list`, `library.work.<id>`, `work.<id>`, `history.list`, `browse.fandom.<i>`, `settings.privacy`, and the reader's (listed in [the reader section](#the-reader-listen-export-and-reading-position)). UI tests depend on them; don't rename one without updating the tests.
- **Large text is a supported setting.** Windows' Text size (up to 225 %) scales XAML text by itself; what breaks is layout that budgets for default-size text. Put text beside an icon in a `"Auto,*"` grid (as `UI.Label` and `AccountKit.KindLabel` do), not a horizontal `StackPanel`, so it can wrap; use `UI.LineLimit(n)` for `maxLines` (no limit from 150 %, `UI.IsLargeText`), including `UI.Label`'s for list rows, chips and menus so they stay one line at normal sizes; `UI.TextScale` is cached and updated from `TextScaleFactorChanged`, so screens pick up a change when they rebuild; scale any fixed height around text by `UI.TextScale`; cap an Auto column's text with `MaxWidthOf`.
- **Narrator is a supported input.** Icon-only buttons get a name (`UI.IconButton`'s label is its tooltip and its Narrator name); headings get `A11yHeading`; decorative icons `A11yHidden`; rows that combine several texts use `AccessibleGroup` (in `LibraryHelpers`), but never wrap something that holds its own buttons. Slow, silent operations announce their result (`MainWindow.ShowMessage` announces; `MainWindow.Announce` for the rest).
- **Keyboard.** `MainWindow` offers every key to the top screen's `HandleKey` first (unless a text box has focus); screens implement shortcuts there. Add new shortcuts to `ShortcutsScreen` and give menu items their keyboard accelerator text.
- **Port faithfully.** Copy the Swift behaviour, names and edge cases, and name the Swift type in the doc comment. Where Windows differs on purpose (haptics hidden, Mica, toasts), say so in the comment.

## Common tasks

**Add a tab.** Add a case to `SidebarItem` in Core (the order of `SidebarItems.All` is the sidebar order), with its raw value, title and SF Symbol name; give it a glyph in `Symbols` if needed and a shortcut in `Shell/SidebarItem.cs`; register its screen with `Tabs.Register` from a `[ModuleInitializer]` in its feature folder; add it to `ShortcutsScreen`, the jump list if it's a common destination, and the smoke tests' tab list.

**Add a route.** Add a factory or action to `Routes`, an `Open…` helper that falls back to a placeholder, and register it from the feature's module initializer. If a deep link or notification should reach it, extend `DeepLink`/`NotificationRoute` in Core (with tests) and `AppRouting`.

**Add a setting.** Pick a key that matches the Swift `@AppStorage` key when one exists, read and write it through `KeyValueStores.Default` (per-device reader keys through `ReaderProfile.DeviceKey`), add the row with `SettingsKit`, and decide whether it belongs in the backup (`SettingsBackup.Fields` in `Sync/LibraryBackup.cs`) or the synced store.

**Add a search filter.** Add the field to `AO3SearchFilters` (its `QueryItems` row, `IsEmpty`, `Merging`, `Clone` and the saved-JSON read and write), a `key:value` token in `SearchSyntax.Parse`/`Render` with a round-trip test, a chip in `SearchChips`, and optionally a control in `WorkFilterSheet`. Only add a natural phrase to `SearchSyntax`'s phrase list if it can never mean anything but the filter.

**Add a parser.** Put it in `Parsing/`, take an HTML string, parse with `HtmlDom`, return a record, and add fixture tests. Fail closed where a wrong empty result could delete data (see `SubscriptionsParser`).

**Add a library field or record type.** Add the property and its column to the entity's `Columns`, `ToRow` and `Read`; for a new type, add it to `LibrarySchema.Tables`, `LibraryEntityKinds`, and `LibraryStore`'s table reads. Append a migration to `LibrarySchema.Migrations` (never edit an existing one; additive only, every new column with a default). Then decide its backup, restore (forward-only, below) and demo-seed behaviour, and add `LibraryStoreTests`.

**Add a test.** Inline fixtures, no network. Use `MockAO3Client`/`StubAO3Client` or a fake `HttpMessageHandler`, `LibraryStore.OpenInMemory()` and `InMemoryKeyValueStore`; join `GlobalStoreCollection` if you touch a static store.

## Things to know about AO3

- No JSON API. We are a respectful guest. The `User-Agent` is `Fanficly/<version> (Windows; https://github.com/yennster/fanficly)` so AO3's operators can find us, without the "(+url)" form web crawlers use; the Apple app's matching `(iOS; …)` and `(macOS; …)` is proposed in #66.
- Work URLs carry `view_adult=true` (skip the age-gate page) and `view_full_work=true` (all chapters on one page).
- **A chapter at a time.** The whole-work page is AO3's heaviest and the one that times out or 503s first, so the readers open on one chapter: `FetchWorkChapterAsync(id, chapter)` loads `/works/<id>?view_adult=true` (AO3 redirects a chaptered work to its first chapter and remembers the consent in a `view_adult` cookie), and for a later chapter follows that page's `select#selected_id` to `/works/<id>/chapters/<chapterId>`. `WorkPageParser.ParseChapterPage` numbers the chapter by its place in that menu, so it matches the whole-work numbering, and sets `IsWholeWork` only when every chapter is there (never from a missing menu). An unreadable page falls back to the whole work. `IAO3Client` gives it a default implementation that returns the whole work, so fakes and the demo client need nothing.
- Chapters are `div.chapter[id^='chapter-']`; the canonical tags are in `dl.work.meta.group`.
- **Login** is form-based: GET `/users/login`, scrape `authenticity_token` (`LoginParser`), POST with cookies. `AO3Client` keeps cookies itself and saves them to the cookie vault, so a session survives restarts. The password is never stored.
- **Subscribe** is a POST to `/works/<id>/subscriptions` with `subscription[subscribable_type]=Work` and the token (`SubscribeToWorkAsync`). Needs login. The work page's options menu calls it and mirrors the result into a local `SubscriptionRecord` (`work:<id>`, baseline today's chapter count); signed out the item opens login, and an expired session offers to sign in again. Any status of 400 or more (422 is a refused token), a redirect to login, or an error flash other than "already subscribed" throws, so it never reads as subscribed.
- **Guest-page parsers fail closed too** (the Swift app's RM-001). `SearchResultsParser`, `WorkPageParser` (both entry points), `MediaCategoryParser` and `WorkFiltersParser` throw `Unauthorized` for the login page (a stale session, or a guest opening a restricted work) and `ParseFailed` for a page without their own markup, so an error page can't read as "No results" or overwrite a saved work; `FetchWorkChapterAsync` still falls back to the whole work when a chapter page fails to parse. The shared test is `AO3PageCheck` (in `SearchResultsParser.cs`): it looks for a login form **inside `#main`**, because every logged-out AO3 page has the header's small login form. A genuine empty page still returns nothing when it carries its listing shell: the index `<ol>`, `#main`'s Rails `controller-action` class (`works-search`, `works-index`, `bookmarks-index`, `fandoms-index`), or AO3's "No results found" / "No fandoms found" line. Fixture shells are `AO3PageFixtures` in `SearchResultsParserTests.cs`.
- **An expired session is its own state (#131).** "Signed in" is only a stored username, so `AuthState.IsSessionExpired` records that AO3 dropped the cookie: `NoteFailure` sets it for `Unauthorized` while signed in, and `NoteListing` for a works listing AO3 rendered for a guest (`AO3SearchResults.ServedAsGuest`, from `AO3PageCheck.IsGuestPage`: the header's login form and no `#greeting` link). A guest listing leaves out every restricted (archive-locked) work, so Search and `PagedWorksList` (author works, bookmarks, readings) pass results through `SessionExpiry.Check` and show its Sign In Again state instead of partial results or a Retry that can't succeed; `LoginScreen` shows the form again with the username filled in, Settings offers Sign In Again beside Sign Out, and signing in (or out) clears it. `HasSession` is what account features need. The poller flags a followed author's guest page while signed in (`SessionExpired`); its public works still alert, and restricted ones alert once a signed-in poll sees them.
- **Subscription sync fails closed.** An expired cookie turns the subscriptions page into the login form. `SubscriptionsParser.ParsePage` throws `AO3Exception` with `Unauthorized` for a login page and `ParseFailed` when there's neither a list nor the page shell; `FetchSubscriptionsAsync` walks every page (50-page ceiling) and throws if any page fails; `SyncSubscriptionListAsync` deletes records only after a non-empty fetch. So markup drift or a stale session can't mass-delete `SubscriptionRecord`s and their `LastSeenChapterCount` baselines.
- **Bookmarks** (`/users/<name>/bookmarks`) list works as `li.bookmark.blurb`; `SearchResultsParser.Parse(html, blurbSelector)` reads them and takes the work id from the `/works/<id>` link (`SearchResultsParser.WorkId`), skipping series and external bookmarks.
- **Creating and editing bookmarks** replays the work page's own form (`bookmarks/_bookmark_form` in `div#bookmark_form_placement`, shown only signed in and prefilled from an existing bookmark), read from `/works/<id>?view_adult=true` (`AO3Endpoints.WorkPage`, not the whole work): a new one posts to `/works/<id>/bookmarks`, an existing one to `/bookmarks/<id>` with a hidden `_method=put`. `BookmarkFormParser` reads the action, hidden fields (token, pseud, or the selected `<select>` pseud), notes, tags, collections (null, and not sent, when the form has no such field) and the `private`/`rec` checkboxes (dropping Rails' hidden `0`s); `AO3BookmarkForm.PostFields` sends them back. A page without the form is `Unauthorized` only when it's signed out (a login form or no username), else `ParseFailed`. After a save, login throws `Unauthorized`, then form errors (`div#error li`, `SaveErrors`) throw `Rejected` first, because a failed update re-renders on `/bookmarks/<id>` too; otherwise the save succeeded only on `/bookmarks/<id>` (`BookmarkFormParser.IsBookmarkPage`, even with a flash there), and any other page throws `Rejected` with its error flash (`FlashErrors`: a refused pseud or account redirects with one) or "AO3 didn't save the bookmark.". After a failed save `BookmarkScreen` re-fetches the form keeping the edits (not when rate limited or signed out), so a retry after a lost response updates rather than duplicates; leaving the screen never cancels a save in flight. Field names come from otwarchive's source, not a live capture.
- **Marked for Later and AO3 History** are `/users/<name>/readings?show=to-read` (`AO3Endpoints.UserMarkedForLater`) and the same page without `show` (`UserReadingHistory`), paginated with AO3's pagy nav (still `ol.pagination` with an inner `.current`). Entries are `li.reading.work.blurb` with id `work_<id>`; deleted works have no id or title link and are skipped. `SearchResultsParser.ParseReadings` fails closed: a login form is `Unauthorized`, and a page without the `div.readings-index` shell is `ParseFailed` (history turned off redirects to `preferences-index`, which gets its own reason). `ReadingListScreen` shows both, login-gated and read-only; AO3 History is separate from the on-device Recently Viewed tab and writes nothing locally. Neither has a Ctrl+number (Ctrl+1–9 are taken, as ⌘1–9 are on the Mac): `SidebarItems.Shortcut` and `ShortcutText` return null for them, and the sidebar, keyboard and Shortcuts screen skip them.
- **Comments** load per chapter (`AO3Endpoints.ChapterComments`, or `WorkComments` for a one-shot) and parse with `CommentsParser` (depth from nested `li.comment`). AO3 pages a thread by top-level comment (`page=`): `CommentsParser.ParsePage` reads the will_paginate list inside `#comments_placeholder`, and `CommentsScreen` appends the next page from a "Load more comments" button (`comments.loadMore`, a footer, not infinite scroll, as on the Mac), skipping ids it already shows. Posting replays the page's own new-comment form (`CommentsParser.NewCommentForm`, `DefaultPseudId`) with the token. Needs login. AO3 answers a refused comment with a 200 page or a followed redirect, so `CommentsParser.PostOutcome` (Swift's `postOutcome`) counts it as posted only on a `div.flash.comment_notice` or a `/comments/<id>` page; an error flash or `#error` list, the POST URL re-rendered, or any other page throws `Rejected`, and the login or `/auth_error` page throws `Unauthorized`. The guest form (`IsGuest`) means the session ended, so nothing is posted. The draft is kept on any error. `CommentsScreen` re-fetches after posting because AO3 may hold comments for moderation.
- **Kudos** (`AO3Client.LeaveKudosAsync`, the Swift `leaveKudos`) mirror AO3's own kudos button, read from otwarchive's source because testing on the live site would leave real kudos. GET the work's first page, require `KudosParser.IsSignedIn` (the `#greeting` link and no login form; AO3 takes guest kudos too, so an expired cookie would otherwise leave one as a guest: Unauthorized, no POST. Not `LoginParser.CurrentUsername`: its `#header` fallback matches the signed-out `/users/login?return_to=…` link), replay `form#new_kudo`'s hidden fields (absent on your own work or when blocked: Rejected, no POST) with the page's **meta** `csrf-token`, and POST them to `/kudos.js`. Not the form's own token: AO3 runs Rails' per-form CSRF tokens, so that one only validates for `/kudos`. `/kudos.js` answers 201 on success, 422 with `{"error_message": …}` for a refusal and 422 with `{"errors": {"auth_error": …}}` for a refused token (Unauthorized); `PerformRequestAsync(passing: [422])` hands the body back, and any other answer is Rejected, not remembered. "You have already left kudos here. :)" counts as `KudosOutcome.AlreadyLeft`. Core's `KudosGiver` and `KudosStore` (work ids in `KeyValueStores.Default`, key `kudos.leftWorkIds`, cleared by `AuthState.LogoutAsync`) hold the state; the app's `WorkKudos` builds the menu item (`work.options.kudos`) and shows the result.
- **Browse** uses `/media/<category>/fandoms`, with category names path-encoded by `AO3Endpoints.AO3PathEncode` (`&`→`*a*`, `/`→`*s*`, `.`→`*d*`, …).
- **Autocomplete** (`/autocomplete/{tag,fandom,relationship,character,freeform}?term=`) must send `Accept: application/json` (the client also sends `X-Requested-With`), and the term must encode `/` as `%2F`, or AO3 answers 404 and tags silently don't resolve.
- **Tag resolution is conservative for freeforms.** `TagResolver.BestFreeformMatch` accepts only the same tag up to case, spacing and punctuation; otherwise it keeps what the user typed. Only authoritative answers are cached; a 429 or offline error falls back for that one search.
- **Rating is single-select** on `/works/search`. One rating goes in `work_search[rating_ids]`; several are OR-ed in the query field (`(rating_ids:12 OR rating_ids:13)`), because the array form AND-matches and returns nothing. Warnings and categories stay arrays.
- **Search never silently reinterprets words.** The box text goes to `work_search[query]`. Tags become filters only when a suggestion is tapped (`other_tag_names`, excludes in `excluded_tag_names`). Only `key:value` tokens and `SearchSyntax`'s short phrase list convert on submit, because AO3 requires every keyword to match. Don't reintroduce guessing.
- **Typeahead:** 350 ms after typing stops, the trailing words go to `/autocomplete/tag` (backing off a word at a time), re-ranked by `SearchSuggestions.RankTags`, memoized in `TagSuggestionCache`.
- **AO3 search is slow:** 20–30 s to first byte is normal. `SearchAsync` uses a 60 s timeout and one retry (other requests 30 s, resource limit 90 s). `SearchScreen` keeps one cancellable search and offers Cancel after 5 s.
- **Filter-only searches sort by kudos** (`SearchSyntax.AutomaticSort`) until the user picks a sort.
- **Saved searches, recents and `fanficly://search?query=`** store `AO3SearchFilters.PromptText()`, which `SearchSyntax.Parse` reads back exactly. The Saved Searches widget sends a saved filter's JSON instead, as the Swift widget does: `DeepLink.SavedFilter` decodes a query that starts with `{`, and `SearchScreen` runs those filters as saved (sort included, and a keyword like "complete" stays a keyword, which reading it back as a prompt would break); anything else, malformed JSON included, runs as a prompt.
- **Popular** is derived from cumulative counts (`FetchPopularSnapshotAsync`: fandom counts from the media pages, ships and characters from the works-filter sidebar of the top fandoms via `WorkFiltersParser`, selector `label[for^='include_'][for*='_{kind}_ids_']`). `PopularStore` caches it (`popular.snapshot.v1`) and refreshes at most daily; the screen falls back to the curated `PopularTags` when a list is empty.
- **Retries:** `AO3Client` retries idempotent GETs only (up to 2 times, 0.5 s then 1 s backoff) on timeouts, dropped connections, and 429 with `Retry-After` of 10 s or less, and never while offline. AO3 being unavailable (502, 503, 504, Cloudflare's 520–526) retries too, after 2 s then 5 s, and then shows "AO3 isn't responding right now". All requests ask for HTTP/3 outright from the first one (`PreferHttp3`, `RequestVersionExact`); where it can't connect (QUIC missing or blocked, a proxy) the request goes again over HTTP/2 and HTTP/2 is used for 10 minutes, and until HTTP/3 has answered once a GET waits at most 5 s for it (two misses also switch to HTTP/2): AO3's Cloudflare edge served HTTP/1.1 and HTTP/2 clients far slower (and with 503/525s) than HTTP/3 browsers. `Fanficly.App.csproj` sets `Http3Support` to true: the trimming targets (pulled in by `IsAotCompatible`, so even Debug) default it to false, which silently kept every request on HTTP/2. Don't remove it. HTTP/3 also needs `msquic.dll` next to `Fanficly.exe` (Windows doesn't ship it, and QUIC itself needs Windows 11 or Server 2022); Native AOT drops it with the runtime pack's other native files, so the csproj's `KeepMsQuicForHttp3` target puts it back and the `package` job's `scripts/Test-PackageFiles.ps1` fails when an `.msix` lacks it. Store 1.0.2 shipped without it and logged "QUIC (HTTP/3) not available". Each request logs one line (method, path, status, HTTP version, time; never the query) to the app's local log, plus once a run what AO3's Alt-Svc header offered on an answer that wasn't HTTP/3, and why HTTP/3 failed when it falls back. Never retry a POST.
- **Throttle:** `Throttle.WaitAsync` reserves the caller's slot before it waits, so simultaneous callers are spaced out rather than released in a burst (a burst is what trips AO3's tarpit).
- **Export:** `/downloads/<id>/work.<ext>` for `WorkExportFormat` Azw3, Epub, Mobi, Pdf, Html (`ExportWorkAsync`, into `%TEMP%\Fanficly\Exports`); EPUB downloads for offline use go through `DownloadEpubAsync`, into `AppPaths.Downloads`. Both refuse a login redirect and, for everything but HTML, an empty body or one starting with markup (`EnsureDownloadedFile`), so a page is never saved as the book.
- **Fail closed on pages that aren't what was asked for.** AO3 answers a signed-in-only request with a 200 at `/users/login`; `FetchWorkAsync`, the chapter and metadata fetches, bookmarks (which also check for the guest login form, since AO3 shows public bookmarks signed out) and comment posts throw `Unauthorized` there. `FetchWorkAsync` throws on a page with no chapters (saving it would replace the stored ones) and `FetchWorkMetadataAsync` on one with no chapter count (reading it as 1/1 would reset the poller's baseline). A comment AO3 refuses re-renders the form at the form's own path, which throws `Rejected` with AO3's message.

## Local follow vs. AO3 subscribe

- **Follow** (bookmark icon) is local only, no login: `WorkPersistence.ToggleFollow` saves the work with `IsFollowed`. `WorkRow` has an inline bookmark button.
- **Follow author** (the Authors tab) is local only: `ToggleFollowAuthor` stores a `FollowedAuthor` with the known work ids seeded, so the first poll doesn't announce the back catalogue.
- **Subscribe** POSTs to AO3 and needs login; it mirrors AO3's own subscription list, which the Subscriptions tab shows next to local follows. Unsubscribing opens AO3 in the browser.

All three feed `SubscriptionPoller`. `RunFullPollAsync` builds one queue of all three kinds, oldest check first (`LastCheckedAt`), stamps each attempt up front, saves after each, and stops on cancellation, so a cut-off run resumes where it stopped. `CheckForNewChaptersAsync`, `CheckFollowedWorksAsync` and `CheckFollowedAuthorsAsync` serve the Subscriptions tab's manual refresh. The poll runs in-app (`InAppPolling`: first after a minute, then every `BackgroundRefresh.DefaultInterval`, 4 hours) and, when packaged, from a timer background task (`BackgroundTaskRegistrar`: 240 minutes, internet required). `FanficlyBackgroundTask` opens its own store and client, runs for about 30 seconds, and skips when the main window is open.

Toasts need no permission on Windows, but the user can turn them off in Windows Settings. The first time a follow asks (`NotificationsAuthorization.RequestAfterFollow` → `Request`, set by `AuthorsModule`) while Fanficly's notifications are off, a dialog offers to open that settings page; it's shown once (`notifications.permissionPromptShown`) and never in demo mode.

**Tapping a toast opens what it's about.** `NotificationRoute` (`NewChapters(workId)`, `NewWork(workId)`, `NewWorks(author)`) is encoded in the toast's arguments (`ToArguments`/`FromArguments`; old work-id-only arguments decode as `NewChapters`). `Notifications.Register()` runs before the window exists so a toast that cold-launches the app is delivered; `NotificationRouter.Shared` holds a route that arrives before the window. `AppRouting.OpenNotificationRoute` replaces the current tab's path with the live work page (`Routes.WorkDetail`) or the author's works, on top of whatever tab is showing.

## Activation, single instance and deep links

`Program.Main` registers the instance under the key `main` (`AppInstance.FindOrRegisterForKey`). A second launch (a protocol link, a jump-list entry, a toast, a share) redirects its activation to the running instance (waiting up to 10 s) and exits; the main instance receives it in `App.OnRedirectedActivation` and brings its window to the front. `AppHost.HandleActivation` handles protocol activation (`OpenUri`), the share target, launch arguments (`-tab <raw>`, or a `fanficly:` or AO3 `https:` link) and toast activation. `AppHost.InstallDropAndPaste` (in `AppRouting.cs`, called from `OnWindowCreated`) also makes the window's root a drop target: a dropped link or text, or Ctrl+V when no text box has focus (`PasteImport`, from `MainWindow`'s key handling after the screen declines the key), goes through `WorkIdFromDataAsync` → `DeepLink.WorkIdFromText` → `ImportOrWarn`, the same path as the share target. A dropped non-AO3 link shows a warning; a paste that isn't an AO3 work link is ignored silently.

`DeepLink.Parse` handles, in `AppRouting`:
- `fanficly://resume/<id>?chapter=&paragraph=` (widgets, jump list): replaces the current path with `Routes.Resume`. `ReaderModule.InstallResumeProgress` asks `ResumeProgressPolicy.AnchorToInstall` what to install: a resume never moves saved progress backwards; only a strictly fresher `WidgetProgressStore` entry from another device may override local progress, and then the store's anchor installs, never the one in the URL. It then opens the saved reader when the work is in the Library, else the live work page, and the reader restores from the installed progress.
- `fanficly://import?url=<AO3 url>`: `ImportOverlay` fetches the work, saves it as followed, downloads the EPUB and opens the saved reader. The share target turns a shared link or text into this route (`DeepLink.WorkIdFromText`); a non-AO3 link shows a warning.
- `fanficly://library?folder=<name>`: selects Library, then opens the folder.
- `fanficly://search?query=<prompt>`: stores the query under `search.pendingQuery`, selects Search and raises `Routes.RequestSearch`; `SearchScreen` runs saved-filter JSON from the widget as those filters (`DeepLink.SavedFilter`) and anything else as a prompt.

## Sync folder backup (merge, never clobber)

Windows has no iCloud API, so sync is a folder the user picks in Settings → Sync (`settings.iCloudSyncEnabled`, `settings.syncFolder`), any folder a sync app keeps up to date. `SyncFolderSuggestions` (Core, tested) finds the installed services and Settings offers a Fanficly folder in each: OneDrive personal and work (the `OneDrive*` variables), Google Drive for desktop (`My Drive` on a fixed drive or in the user folder), Dropbox (`info.json`, else `~/Dropbox`), Box and iCloud Drive, preferring the Apple app's container (`iCloud~io~github~yennster~fanficly/Documents`) so a Mac and a PC can share one backup. Turning sync on with no folder chosen uses the first one found (OneDrive when set up); with none, the folder picker opens.

- **Backup unions, never overwrites.** `LibrarySyncManager.Backup` reads the existing `library_backup.json` and merges it with the local snapshot (`MergedBackup`, pure and tested) before writing: records only in the file are kept; on conflict the local record wins, except where a field only moves forward: works merge field by field with `MergedWork` and subscriptions with `MergedSubscription` (the helpers restore uses too, so the rules hold in both directions; only follow/star/pin keep this PC's values in the file, so an un-follow can reach it, and restore ORs them), reading positions keep the newer `UpdatedAt`, and stats merge conservatively (`MergedStat`: total seconds never below the sum of day buckets). A `.library_backup.json.icloud` placeholder means the file isn't downloaded, so the backup skips. So does a file that's locked (`FileBusy`) or won't decode (`Unreadable`, left untouched with the reason in `LastBackupError`): only a missing file starts from the local snapshot alone. Each write first copies the file it replaces to `library_backup.prev.json` (`PreviousBackupPath`); Clear Synced Data deletes both. A backup whose merged result is what the file already holds (`SameBackupContent`: the parsed JSON, ignoring `timestamp`) writes nothing and returns `Unchanged`, so the sync app doesn't upload the library again. The snapshot reads chapter bodies that aren't loaded through `Chapter.BodyForBackup`, which doesn't keep them, so a backup doesn't leave the whole library's text in memory.
- **Restore is strictly forward** and runs automatically at launch when the file changed since this PC last applied or wrote it (`CloudBackupHasUnappliedChanges`, stamp `icloud.lastRestoredBackupDate`). A backup stamps the file it wrote only when the file it merged with held nothing this PC hadn't applied; merging in another device's unapplied records leaves the stamp, so the next launch still restores them into the library (they went into the file, not the store). Each existing work merges with the backup's copy through `MergedWork`: AO3 metadata (Title through UpdatedAt) comes whole from the fresher copy (later `UpdatedAt`, then more chapters, then more hits; a tie keeps local), `SavedAt` keeps the later date, positions apply only when newer, follow/star/pin are OR-ed, folders union, `LastSeenChapterCount` only advances (on works and subscriptions, and a subscription's `LastCheckedAt` keeps the later date: `MergedSubscription`), chapters replace only when the backup has more. Keep any new restore field forward-only or the second device to open will corrupt data.
- **EPUB re-download:** the backup carries chapter text, not EPUB files; after a restore `RestoreDownloadCenter.ProposeRedownload` offers to download them again (the `RestoreBanner`, cancellable, paced by the throttle).
- The JSON format is the Swift app's (`LibraryBackupJson`, ISO 8601 dates). `SettingsBackup.Fields` carries the per-device reader keys for phone, pad, Mac and Windows (`reader.*.windows`) and each device's active profile (`activeProfileWindows` is Windows-only). Each app keeps the keys it doesn't know when it rewrites the file (`BackupUnknownKeys` here, `iCloudSyncManager.preservingUnknownKeys` in Swift): top-level keys whole, unknown keys of each record and chapter the file also has, and `settings` key by key. Keys this app knows are never copied back, since a missing one can mean cleared, so **add every new backup field to `BackupUnknownKeys`' known sets** too (`KnownKeySetsListEveryBackupRecordField` fails until they match the record constructors, and `KnownKeySetsCoverEverythingTheEncoderWrites` checks the encoder's keys). The Apple app's `note`, `personalTags` and `notesUpdatedAt` are kept that way until Windows knows them; RM-009's port (#122) adds them to `WorkBackup`, and must add them to `WorkKeys` in the same change. `blocked` entries have no single identity key (kind plus value), so they're not matched record by record: a field one app adds to them is dropped by the other until both know it. Followed authors are backed up under an optional `followedAuthors` array (username, display name, `followedAt`, `knownWorkIds`, `lastCheckedAt`), matched by username ignoring case: the merge and the restore union `knownWorkIds`, keep the earliest `followedAt` and the latest `lastCheckedAt`, and a restore only adds follows. The Swift app doesn't read it yet (RM-022 in `main`'s roadmap, proposed in #65). Not backed up: recently viewed and tags (as in Swift).

## Reader settings profiles

Typography settings are per device (`ReaderProfile.CurrentDevice = ReaderDevice.Windows`, keys like `reader.theme.windows`, active profile `reader.activeProfile.windows`). Profiles are JSON under `reader.profiles`, managed in Settings → Reader (new, rename, delete, switch). `ReaderProfileSyncStore` mirrors that key through the synced store, merging by case-insensitive name (`MergedProfiles`). Deletions are tombstones (`DeletedAt`), kept 90 days so they propagate; the newest stamp wins per name. Legacy unsuffixed keys migrate once (`MigrateLegacySettingsIfNeeded`).

## Reading stats

`ReadingStat` (one row per work id) snapshots the work's metadata, accumulates active reading seconds per day (`DaySeconds`, `yyyy-MM-dd`), and keeps `MaxProgress` (only advances) and `WorkIsComplete`. `ReadingStatsStore` upserts; `ReadingStatsAggregator.Summarize` rolls up a period (pure, tested). Words read are `Σ wordCount × MaxProgress`; stories read count only finished works (`MaxProgress ≥ 0.99`, or `≥ 0.95` for a complete work). `ReadingStatsBackfill` seeds rows once from older history. The Stats tab (`StatsScreen`) shows Week / Month / Year / All Time (default All Time) with paging, and shares a `WrapShareCard` image (Share, Save Image As, Copy Image). The Library shows a `LibraryStatsStrip` that opens Stats. The yearly reading goal (RM-011, the Swift `ReadingGoal`) is `reading.yearlyGoal` in `KeyValueStores.Default` (0 = none; per-device, not in `SettingsBackup`); the Stats tab shows its ring on All Time and the current year, the wrap card adds a goal row there, and pace is the pure `ReadingStatsAggregator.GoalProgress`. `GoalRing` draws the ring with shapes so the wrap card's image can't depend on `ProgressRing`'s animated visual rendering into a bitmap. Result rows (`WorkRow`) and the work header show a reading-time estimate ("~45 min") from `ReadingSpeed`: the reader's pace, the median of each finished, timed work's pace (each clamped to 120–600 wpm, so one skimmed or re-read work can't swing it), 250 until there are three such works, cached until a stat saves; nothing is stored. Recording time and progress happens in the reader (see [the reader section](#the-reader-listen-export-and-reading-position)).

## The reader, Listen, export and reading position

`Views/Reader` holds the screens and the WinUI reader; the pure logic it builds on is in Core and tested (`HTMLToAttributed`, `ChapterTracking`, `ChapterAnchors`, `ReaderAnchorSampler`, `ReaderPaginator`, `ReaderTheme`, `ReaderMetrics`, `ReaderSpread`, `PageAreaTracker`, `ReaderProfile`, `SentenceSegmenter`).

- **Routes** (`ReaderModule`): `Routes.WorkDetail` → `WorkDetailScreen` (fetches the work, records the view, then the reader); `Routes.SavedWork` → `SavedWorkReaderScreen.ForWork` (reads the saved chapter text offline when there is any, else fetches the work; falls back to the live page when the work isn't in the Library). Fetching opens on the saved chapter's page (`ReaderView.FromChapterPage`, which reckons progress against the whole work's chapter count so finishing one chapter never finishes the story), then `ReaderHostScreen.FetchRestAsync` loads the whole work behind it (retried, and held while Listen plays) and `SwapReader` replaces the reader in place (`ContinueFrom`, then `Retire`, which saves time and position without the closing review prompt). Saving offline always uses the whole work, never the one-chapter payload; `Routes.Resume` → installs progress (above) and opens one of the two. Both screens derive from `ReaderHostScreen`, which shows the loading or error view in the reader's colours, hides the window header once the reader exists (the reader draws its own top bar in its theme) and forwards `OnAppearing`/`OnDisappearing`/`OnRemoved` and `HandleKey` to `ReaderView`. `ReaderView` is not a screen: it's split by concern into `ReaderView.cs` (state, lifecycle, position, timing, keys, Narrator menu), `.Chrome` (top bar, chapter indicator, page footer, Listen bar, chapters and Aa menus, profiles), `.Content` (title and chapter headers), `.Continuous`, `.Paginated` and `.Pages`.
- **Toolbar.** The reader's own items: Back (only in full screen, when the stack can go back), Chapters (multi-chapter works), Aa (reader settings) and Full screen. The parent adds exactly two through `SetTrailingItems`: the work page adds Save to Library (`work.save`, a local follow) and Work options (`work.options`: `work.options.comments`, `work.options.kudos`, `work.options.bookmark`, Share & export (`work.export`), `work.options.download`, `work.options.subscribe`, `work.options.report`, `work.options.hide`); the saved reader adds Comments (`work.comments`, which resolves missing chapter ids from AO3 once for per-chapter threads) and More (`work.options`: `work.options.kudos`, Bookmark on AO3 as `work.options.bookmark`, Share & export, Save Offline as `work.options.download`). Anything a menu item presents is deferred through the dispatcher (`Later`, `PresentLater`, `WorkExporter.Start`, `WorkKudos.Start`) so the flyout has closed first. Busy states swap the menu icon for a spinner.
- **Aa menu:** Listen to chapter (`reader.listen`, Ctrl+L), Profile (select, save current settings here, rename, delete, save current as new), Reading mode, Pages on screen (page-by-page only), Theme, Font, Bold text, and presets for text size, line spacing, paragraph spacing, character spacing and margins ("Page margins", `reader.spreadWidthPercent`, while a spread is on screen). Every value is a per-device key through `ReaderPrefs` (`ReaderProfile.DeviceKey`). Settings → Theme & typography has the same settings as sliders with a live preview. A change to a profile key queues a backup. The reader divides every typography value by `app.zoomScale`, so the app's zoom leaves story text alone.
- **Three reading modes** (`ReadingMode`, default continuous):
  - *Continuous scroll*: one `ItemsRepeater` (virtualized) of title header, chapter headers and paragraphs, converted off the UI thread; a chapter indicator bar (`reader.chapterIndicator`) for multi-chapter works; a tap anywhere toggles the controls.
  - *Swipe by chapter* (`paginated`): a `FlipView` with one vertically scrolling chapter per item (only the chapter on screen and its neighbours are built) and a `PipsPager`; Left/Right change chapter, Page Up/Down and Space scroll a screenful and roll into the next chapter at the end.
  - *Page-by-page*: a `FlipView` of pages, or spreads; selection is always a page id. Pages near the one on screen (two either side, or one spread) are built, the rest freed.
- **The text column** is `ReaderMetrics.TextColumnWidth(width, margins %)` with `limitLineLength: false`: the margins setting alone sets the line length, with no 40 em cap on Windows.
- **Two-page spread.** `reader.twoPageSpread` (default on). `ReaderSpread.LayoutFor`: at least 700 px wide, at least 1.15 × as wide as tall, and two pages of at least 280 px around a 56 px gutter, which is blank (no drawn crease). It's decided on the controls-up height (`PageAreaTracker.SpreadDecisionHeight`), so hiding the controls never switches between one page and two. Pages pair within a chapter; the footer reads "Pages 3–4 of 12". The title page keeps at least the default spread width so its metadata isn't crushed.
- **Pages fill the area on screen.** `PageAreaTracker`: a new width or window height starts over; otherwise pages shrink at once, so text never runs under the controls, and grow once the area holds still for 0.3 s (50 ms when the controls toggle). Pagination is debounced 60 ms and skipped when nothing in its `PaginationTrigger` changed. `ReaderTextMeasurer` measures real XAML `TextBlock`s built by the same `ReaderText` code that draws the page, parented in an invisible host inside the reader so they lay out at the window's scale; it clears its cache when the `XamlRoot` changes. Every page is checked against the drawn layout, including the neighbouring chapters (`ReaderPaginator.ChecksAdjacentChapters`, true by default on Windows), so pages fill to the last line with no reserve.
- **Re-paginating keeps the page in place.** The reader tracks where the page on screen begins (`PageStart`: paragraph, sentence, offset; in a spread, the left page's) and `ReaderPaginator.PerformPagination` breaks a page exactly there on a resize, a typography change, the controls or the Listen bar showing or hiding, so lines come and go at the foot instead of the page jumping. A kept page that pairing would put on the right is marked `StartsSpread`. A chapter change re-paginates around the new chapter.
- **Turning.** Keys reach `ReaderView.HandleKey` before anything else (unless a text box, menu item, slider, combo box, list item, radio button or pips pager has focus): Left/Right, Page Up/Down, Space and Shift+Space, LT/RT and D-pad left/right turn a page (the D-pad only while no button has focus, so it can still move along the toolbar) (or a spread; in the scrolling modes, a screenful, and Left/Right change chapter in swipe by chapter); Ctrl+Left/Right and LB/RB change chapter (announced "Chapter n of m"); Home/End go to the chapter's first or last page or edge; Up/Down turn a page in page by page (several Bluetooth page turners send only those; not while a button has focus) and scroll 48 px in the scrolling modes; Ctrl+L toggles Listen; Esc leaves full screen, else shows hidden controls. Pointer: the outer thirds of the page area turn (in a spread, the left page's outer side goes back), the middle third toggles the controls, the mouse wheel turns one page per notch with a 300 ms pause (a page that overflows scrolls first), a quick sideways pen stroke turns, and touch swipes the `FlipView`. Ctrl+wheel never zooms the reader. Page turns animate only when "Page-turn animation" and Windows' animation setting allow.
- **Narrator.** The reading area's context menu (right-click, press and hold, Shift+F10, Menu key) holds Next/Previous page (page-by-page), Next/Previous chapter, Show/Hide reader controls and Listen to chapter / Stop listening; page, chapter and controls changes are announced. Story text isn't selectable (`IsTextSelectionEnabled = false`). Regions are `RegionGrid`s, which give a plain grid an automation peer so its id is visible.
- **Automation ids:** `reader.root`, `reader.content` (the body of whichever mode), `reader.back`, `reader.chapterTitle`, `reader.chapters`, `reader.aa`, `reader.fullscreen`, `reader.listen`, `reader.chapterIndicator`, `reader.pageFooter` (its name is "<chapter>, page n of m" / "pages n–m of t", or "Laying out pages"), `reader.page.left` / `reader.page.right` (only the page or spread on screen, named "Page n of m, chapter c"), `reader.narrationBar`, `speech.playPause`, `speech.chapter`, `speech.rate`, `speech.stop`, plus the parents' `work.*` ids above.
- **Full screen** is the window's (F11, the button): `EnterImmersive` hides the sidebar and title bar (`MainWindow.SetChromeHidden`) and the reader's controls; leaving the reader leaves full screen.
- **Reading position** is saved per work (`ReadingProgress`: chapter, paragraph, plus a 0…1 fraction) through `ReadingProgressStore`, which also stamps `Work.LastRead*`, the streak, the last-read widget and the jump list. Saves are throttled to one per 1.5 s and forced on leaving, minimizing and closing the window. Continuous and swipe-by-chapter report anchor offsets (every `ChapterAnchors.AnchorStride` (6) paragraphs plus always the last) to `ReaderAnchorSampler`, which is resize-aware and takes a trailing sample where scrolling settles; the end of content is detected explicitly (`ChapterTracking.EndOfContentAnchor`), and page-by-page anchors to the last paragraph on the work's final page (or the right page of the final spread), so a story read to the last line reaches 100 % and counts as finished. A saved place in a chapter the reader doesn't have (a notification opened the live work past the downloaded copy) is moved onto the last loaded paragraph before it (`ChapterTracking.ClampedAnchor`) and that moved place is never saved, nor a fraction for an unloaded chapter, so opening a shorter copy never resets progress. Restore: continuous lands on the paragraph repeatedly while heights settle, swipe by chapter restores its paragraph once, page-by-page selects the page holding the anchor. A width change re-anchors the scrolling modes to the paragraph that was on top. Switching modes keeps the live anchor.
- **Reading time** counts only while the reader is the screen on top and the window isn't minimized (`MainWindow.VisibilityChanged`), capped at 4 hours a span, flushed when the reader leaves the top, the window is minimized or closes, and checkpointed with progress saves once a span passes 2 minutes. Words are credited only up to the progress reached. The read that finishes a story calls `ReviewPrompter.StoryFinished`, and `ReaderClosed` is asked when the reader is popped (`Removed`), never when a screen is pushed over it.
- **Story images** are opt-in (`reader.showImages`, default off), and only ever load in works rated General or Teen (`ContentFilter.AllowsStoryImages`): Mature, Explicit, Not Rated and unknown-rating works stay text-only, because the Microsoft Store bans apps that display pornographic content (policy 11.7) and the IARC rating answers say the app shows no pornographic images. `ReaderView.ShowImages` combines the two; use it, not `ReaderPrefs.ShowImages`, inside the reader. When on, images render in fixed-height slots (`ReaderInlineImage.SlotHeight`, 240) in every mode so loading can't move the text; the paginator budgets the same height. `HTMLToAttributed.ResolvedImageUrl` allows only https (http upgraded, protocol-relative resolved) and rejects `data:`, `javascript:`, root-relative and `archiveofourown.org` sources. `ReaderText.ImageSlot` loads them with a XAML `BitmapImage`, outside `IAO3Client`: no throttle, and never the client's AO3 cookies. A failed load shows "Image unavailable". Images are never saved with downloads, so offline they don't load. Toggling the setting shifts paragraph indices, so a saved position can drift by the number of images above it (as in Swift).
- **Listen (text to speech)** is on-device: `SpeechController` renders each paragraph with `Windows.Media.SpeechSynthesis` (voice `reader.ttsVoiceId`, empty = system default; rate `reader.ttsRate` on the Apple scale, 0.5 = 1.0×) a few paragraphs ahead into a `MediaPlaybackList`, so playback is gapless. It speaks `HTMLToAttributed.SpeechParagraphs`, index-aligned with the rendered paragraphs (scene breaks and images are empty, unspoken slots), starts from the current anchor, highlights the spoken paragraph (a flush background, no reflow) and keeps it in view or turns to its page, and advances chapters on its own (`Finished` → `AdvanceNarration`). The Listen bar (`reader.narrationBar`) has previous/next paragraph, play/pause, a chapter picker (multi-chapter), "¶ x / y", a speed menu (0.5×–2.0×, persisted) and stop. `SystemMediaTransportControls` give media keys, headsets and the Windows media flyout play/pause/next/previous and show chapter, author and work. Narration keeps playing while the window is minimized (from `Play` to `Stop` the process opts out of Windows 11's execution-speed throttling, `Platform/PowerThrottling`, so synthesis stays ahead of playback) and stops when the reader leaves the top. If synthesis fails, an InfoBar points to Settings → Time & language → Speech.
- **Export** (`WorkExporter`, owned by the screen, never by menu content): "Share & export…" lists AZW3, EPUB, MOBI, PDF and HTML for the share sheet (`DataTransferManager` for the window), and "Save a copy as" the same formats through a `FileSavePicker`. The download goes through `ExportWorkAsync` (so the throttle applies), is announced, and failures show an alert.
- **Download / Save Offline** saves the full work (`WorkPersistence.Upsert`) and its EPUB (`DownloadEpubAsync`); the item then reads "Downloaded".
- **Keep screen awake:** `reader.keepScreenAwake` (default on) holds a `DisplayRequest` while the reader is on top and releases it when it leaves.
- **Layout UI tests:** `ReaderLayoutTests` (see [Tests](#tests)). Run them after any change to the reader's layout, the measurer or the paginator.

## Store art capture mode

`-captureScale N` (demo mode only, `Platform/CaptureMode.cs`) draws the whole window at N× through a `ScaleTransform` on the root, hides the system caption buttons (drawn instead as glyphs in the title bar, since they can't scale), and subclasses the window (`WM_GETMINMAXINFO`) so it may be larger than the screen. The UI tests' `store` sizes use it so a small CI screen still gives 4K pictures; `PrintWindow` draws the off-screen part. Keyboard and UI Automation patterns reach the whole window, mouse clicks only the on-screen part, so Store-size steps drive the app by keyboard and `Invoke`. It changes nothing outside demo mode.

## Privacy posture (do not regress)

The app stores nothing off the PC except, when the user turns sync on, the backup and synced-settings files in a folder they choose (their own OneDrive, iCloud Drive or other synced folder). It talks only to archiveofourown.org, plus image hosts when the user opts into story images. No analytics, crash reporting or remote logging. The only secret is AO3's session cookie, DPAPI-encrypted. See `PRIVACY.md`; it's the Store listing's privacy policy, so update it with any change to what's stored or sent.

## CI

`.github/workflows/windows-ci.yml` runs on pull requests to `main` and pushes to `main` that touch `windows/` or the Windows workflows. The Apple `ci.yml` runs only for `apple/**`, so a PR builds just the app it changes. A newer push waits for the running build rather than cancelling it.

- **Core tests:** `dotnet test` in Release on `windows-latest`, results as `core-test-results`.
- **App (x64, ARM64):** unpackaged self-contained Debug builds; the x64 build is launched in demo mode and photographed (`launch-screenshot`).
- **UI tests and screenshots:** builds the app and UI tests, sets a 1920×1200 display, installs the Windows 11 icon font, runs `SmokeTests`, then `ScreenshotTests` (the three sizes, the store sizes, the reader pages and the icon gallery), then `ReaderLayoutTests`, charts the icon fonts, builds the Store art into `ui-screenshots/store-art/` (not committed) with `make_store_art.py --out`, prints the pictures into the log and uploads `ui-screenshots` (including `icons/` and `reader-layout/`) and `ui-test-results`. The screenshot and reader layout steps run even when an earlier step failed.
- **MSIX bundle:** after Core tests and App pass, MSBuild builds the Release (Native AOT) x64 + ARM64 Store upload (`msix-bundle`). This is the only job that compiles with AOT, so it's where trim and AOT problems surface.

`windows-screenshots.yml` (`contents: write`; a push to `main` whose message contains `[screenshots]`, or a manual run from the Actions tab) builds the app, runs `ScreenshotTests`, copies the pictures with `windows/scripts/Copy-Screenshots.ps1` to `windows/docs/screenshots/{desktop,tablet,compact}/`, builds the Store art with `windows/scripts/make_store_art.py` (ten 3840×2160 slides with `captions.txt` in `windows/store/screenshots/en-us/`, the hero, box and poster in `windows/store/images/en-us/`, and `windows/docs/screenshots/showcase.jpg`), and commits them to the branch it ran on (a manual run on a PR branch commits there; on `main` it pushes straight to `main`, so branch protection on `main` must let the workflow push). That's release housekeeping: a maintainer runs it, roadmap PRs don't.

`windows-store.yml` (a `windows-v*` tag or a manual run) builds, runs the Windows App Certification Kit, submits to the Store (environment `microsoft-store`) and makes a GitHub release; see `MICROSOFT_STORE.md`. CI picks the runner image's tools; don't hard-code machine-specific paths.

## Autonomous roadmap work

The backlog is [`windows/ROADMAP.md`](ROADMAP.md). Windows items are numbered from **RM-101** so they never collide with the Apple roadmap's IDs (`apple/docs/ROADMAP.md`). This loop is for an agent told to "pick a roadmap item and ship a PR". It ends at an **open PR against `main`**. A human merges.

**Hard rules**
- Never merge a PR, enable auto-merge, approve your own PR, push to `main`, force-push a branch you didn't create, or edit CI to make it pass.
- Never touch release housekeeping: `windows/store/` (version, listing, screenshots), the manifest's `Identity` and version, `windows/docs/screenshots/`, signing settings, the Store workflow.
- Don't change the Apple app's sources in a Windows PR; they are the reference. One roadmap item per PR, one agent per item; don't start an item that's claimed.
- Don't reformat or refactor what the item doesn't need. Don't add dependencies.
- Don't create GitHub issues, labels or releases. Anything outward-facing beyond the one PR needs the user's say-so.

**The loop**
1. **Orient.** `git fetch origin && git checkout -b tmp origin/main`; read Conventions, "Things to know about AO3" and the roadmap's principles.
2. **Pick.** `.github/scripts/roadmap.sh free windows` (needs `gh`) lists open, unclaimed items from the Windows roadmap. Take the lowest-numbered `S` or `M` item unless the user named one; prefer `Validation: unit` when you can't run Windows. If nothing is free, stop and say so.
3. **Verify it's real.** Read the files the item names. If it's already done, wrong, or bigger than `M`, open a roadmap-only PR that fixes or splits it, or report back.
4. **Claim before coding.** Branch `roadmap/RM-1nn-short-slug` from `origin/main`, push, and open a **draft PR against `main`** (`gh pr create --draft`) titled `RM-1nn: <title>`. Re-run `.github/scripts/roadmap.sh`; if another claim for the same ID appeared, close yours and pick again.
5. **Implement the smallest slice** that meets "Done when", following the Conventions (the client seam, pure parsers, `KeyValueStores`, Narrator names, AOT rules).
6. **Test.** Core tests for every behaviour change; a smoke step for a new tab or route.
7. **Validate honestly** (below).
8. **Update the roadmap** in the same PR: that item's `Status` to `done`, nothing else. Update this file if you added a convention or found a gotcha.
9. **Commit, push, mark ready** (`gh pr ready`) when CI is green or the failure is explained. Report the item, the PR URL, what you tested and what a person should look at on Windows.

### Which machine you're on

- **Windows:** run the Core tests, build and run the app in demo mode, and run the smoke tests for UI changes (and `ReaderLayoutTests` for reader layout changes). For packaging-related changes, build the Release bundle with MSBuild.
- **Linux or macOS:** install the .NET 10 SDK (the repo's `.agents/setup` prepares the Apple-side tooling only). You can run `dotnet test tests/Fanficly.Core.Tests` and compile the app and UI tests, which catches most errors. You can't run the app, the UI tests or the AOT build; CI does those on the PR (`gh pr checks <pr> --watch`). Keep the PR in draft until the build and tests are green, and say plainly what you couldn't run.
- Either way, never claim a test passed that you didn't see pass.

**If you get stuck:** three failed CI attempts at the same error, or AO3 behaviour you can't confirm without the live site → stop, leave the draft PR with what you learned, and say what you need. Scrape fixtures must come from real pages.

**Adding to the roadmap:** append items with the next free `RM-1nn`; never renumber or reuse an ID. Keep each item `S` or `M` with a concrete "Done when".
